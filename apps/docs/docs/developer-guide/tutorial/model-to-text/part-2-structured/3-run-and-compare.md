# 3. Run and compare

The package is the one Part 1 built, with a reorganized template and
two new rules. Nothing about packaging it or running it has changed.

## The manifest

```json
{
  "kind": "m2t",
  "entry": "./dist/transformation.js",
  "exportName": "RelToSqlStructuredTransformation",
  "source": {
    "metamodel": "@synthesis/standard-metamodels/rel-tutorial"
  },
  "target": {
    "metamodel": "text"
  }
}
```

Field for field the same as Part 1's, except for `exportName`, which
names this part's class. The number of files a transformation produces
is not something the manifest knows or needs to know: it follows from
the documents in the result.

## Build, install, run

```bash
npm run build

synth init
synth namespace mk demo
synth model import sample/library-rel.tsx --as demo/library-rel

synth transformation install .
synth transformation run sql-tutorial-structured --in demo/library-rel --out-dir ./generated
```

```text
Running sql-tutorial-structured@0.1.0 (m2t) on demo/library-rel
Wrote /home/you/work/generated/Library_rel.sql
Wrote /home/you/work/generated/Library_rel-constraints.sql
```

Two documents, two `Wrote` lines, in the order the documents appear in
the template. The sample model is the same file Part 1 used, so if you
still have `demo/library-rel` in your workspace from Part 1 there is
nothing to import again.

## The tables file

```bash
cat generated/Library_rel.sql
```

```text
-- Tables of Library_rel, generated by Synthesis
 
CREATE TABLE Book (
  bookId INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  bookTitle VARCHAR(255),
  AuthorId_FK INTEGER
);
 
CREATE TABLE Author (
  authorId INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  authorName VARCHAR(255)
);
 
CREATE TABLE Category (
  categoryId INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  categoryName VARCHAR(255)
);
 
CREATE TABLE categorizedAs (
  BookId_FK INTEGER NOT NULL,
  CategoryId_FK INTEGER NOT NULL
);
 
```

Beside Part 1's file, three differences and no more.

- The header comment is different text, from a different header
  section.
- `AuthorId_FK INTEGER` has lost its `REFERENCES Author(authorId)`, and
  the two join table columns have lost theirs. The columns and their
  `NOT NULL` clauses are untouched: a foreign key column is still a
  column, and the constraint is what moved.
- Everything else is identical, including the order of the tables,
  which is still the order they appear in the schema.

## The constraints file

```bash
cat generated/Library_rel-constraints.sql
```

```text
-- Foreign key constraints of Library_rel, generated by Synthesis
-- Apply after Library_rel.sql: references may be circular, so
-- every table has to exist before any of them is constrained.
 
ALTER TABLE Book ADD CONSTRAINT fk_Book_AuthorId_FK
  FOREIGN KEY (AuthorId_FK) REFERENCES Author(authorId);
 
ALTER TABLE categorizedAs ADD CONSTRAINT fk_categorizedAs_BookId_FK
  FOREIGN KEY (BookId_FK) REFERENCES Book(bookId);
 
ALTER TABLE categorizedAs ADD CONSTRAINT fk_categorizedAs_CategoryId_FK
  FOREIGN KEY (CategoryId_FK) REFERENCES Category(categoryId);
 
```

Three foreign keys, which is the same three the inline clauses of Part
1 expressed: the one on `Book` that came from the 1:N relationship, and
the two on the `categorizedAs` join table. `foreignKeysOf` walks the
tables in schema order and the columns in table order, so the
statements come out grouped by table without anything sorting them.

Each statement is two lines and a separator, because
`foreignKeyToAlter` emits three paragraphs. The continuation line is
indented by the two spaces at the front of its template literal.

Applied in order, the two files produce the schema Part 1's single file
produced. The difference is that they also produce it for schemas whose
references are circular, which no single file with inline clauses can.

## The two halves of the tutorial, again

The sample model is the output of `eer-tutorial-basic`, so this
generator can be run as the second step of a chain in exactly the way
Part 1's can:

```bash
synth transformation run eer-tutorial-basic sql-tutorial-structured \
  --in demo/library --out-dir ./generated
```

An EER schema goes in and two SQL files come out, with the relational
schema existing only in memory between the steps.

## Both packages are smoke tested

Every example in the repository is exercised by the same script, which
runs the full CLI loop in an isolated workspace and fails loudly if any
step does. For these two packages it reports:

```text
sql-tutorial-basic: OK (generated Library_rel.sql)
sql-tutorial-structured: OK (generated Library_rel-constraints.sql, Library_rel.sql)
```

That line is the reason the listings on these pages can be quoted
verbatim: the packages are built and run in CI, so a change that breaks
them breaks the build rather than quietly making the tutorial wrong.

## Where you are

You have taken one generator and changed how its output is organized,
twice, without touching what it generates. Content is placed by name
rather than by where its rule was written, and the file structure is
declared in one readable place at the top of the template.

Which leaves an obvious question hanging. Part 1 committed to one file.
Part 2 committed to two. Both are defensible, and nothing in a
relational schema says which is right: a small schema deployed by hand
wants one script, a schema with circular references needs the split,
and a schema kept under review per table might want one file per table.
The model cannot answer that, because it is a property of the project
the DDL is deployed into.

A question the source model cannot answer is exactly what a variation
point is for.
[Part 3](../part-3-configuration-based/index.md) declares the layout as
an issue with options, binds it to the source metamodel, and lets a
configuration model close it per run.
