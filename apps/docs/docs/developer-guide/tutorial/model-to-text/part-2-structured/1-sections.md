# 1. Sections

In Part 1 a rule's output ended up where the rule was called:

```tsx
<Doc name={`${s.name}.sql`}>
  <Sec name="header">...</Sec>
  {this.tablesOf(s).map((tab) => this.tableToCreate(s, tab))}
</Doc>
```

The `map` sits inside the document, so the sections it returns are
nested in the document, so their lines are in the file. Placement is
nesting, and nesting is a property of where the call was written.

That is fine for one file with one kind of content. It stops being fine
as soon as a rule's output belongs somewhere the rule is not written,
which is exactly what happens on the next page, where one walk over the
schema feeds a different file from the one the table rule feeds.

## Sections as addresses

Part 2's template declares the document structure first, as empty
scaffolding, and lets the rules fill it in by name:

```tsx
  template(s: rmT.IRelSchema) {
    return (
      <M2T name={`${s.name}_sql`}>
        {/* The two files, declared as empty scaffolding. Everything
            below fills them in by name. */}
        <Doc name={`${s.name}.sql`}>
          <Sec name="tables-header">
            <P>{`-- Tables of ${s.name}, generated by Synthesis`}</P>
            <P>{' '}</P>
          </Sec>
          <Sec name="tables"></Sec>
        </Doc>
```

`<Sec name="tables"></Sec>` has no children. It is a named region of
the first document, and it exists so that something else can point at
it. Read the template and you can see the shape of the output without
reading a single rule: a header, then the tables.

The rule that produces a statement now sits at the top level of the
model and says where it belongs:

```tsx
  // Produced at the top level of the model, placed into the `tables`
  // section of the first document. The column lines carry no REFERENCES
  // clause any more: the reference has moved to the other file.
  tableToCreate(tab: rmT.ITable): ExprNode<m2tmm.ISection> {
    const cols = tab.columns ?? []
    return (
      <Sec name={`table_${tab.name}`}>
        <SecParent $refByName="tables"></SecParent>
        <P>{`CREATE TABLE ${tab.name} (`}</P>
        {cols.map((c, i) => (
          <P>{`  ${this.columnLine(c)}${i < cols.length - 1 ? ',' : ''}`}</P>
        ))}
        <P>{');'}</P>
        <P>{' '}</P>
      </Sec>
    )
  }
```

Everything but the first child is what Part 1 wrote. The new line is:

```tsx
<SecParent $refByName="tables"></SecParent>
```

and it is the whole mechanism of this page.

## How `SecParent` works

`Sec` and `SecParent` are two tags over the same `Section` concept, and
what separates them is what nesting one of them means.

- `<Sec name="tables">` nested inside a document or another section
  becomes a child of it. Nesting is containment, which is how Part 1
  built its single document.
- `<SecParent $refByName="tables" />` written inside a section creates
  nothing. It names a section that already exists and makes that
  section the parent of the one it is written in.

So a rule that returns a section carrying a `SecParent` is saying where
its output belongs instead of being written there. Because the
metamodel declares

```ts
t.inverseProps(Section, 'elements', DocElement, 'parentSection');
```

setting `parentSection` puts the element into the named section's
`elements` collection. Naming your parent and being nested in it are
two ways of writing one fact, and the metamodel keeps them in step.

The direction is worth stating in plain terms, because the tag is easy
to read backwards. `<SecParent $refByName="tables" />` inside
`table_Book` means "`table_Book` belongs to `tables`". It does not mean
"`tables` belongs here".

## Where the top-level sections go

The rules are called at the top level of the model:

```tsx
        {this.tablesOf(s).map((tab) => this.tableToCreate(tab))}
        {this.foreignKeysOf(s).map((fk) => this.foreignKeyToAlter(fk))}
      </M2T>
```

These sections are children of `<M2T>`, not of any document. They are
model elements, and they are reachable in the store, but they are not
part of any document's element tree until `SecParent` places them
there.

This is worth understanding rather than memorizing, because it explains
the failure mode. Text generation walks the model's `items`, which holds
the documents, and serializes each document's element tree. A section
that no document contains is never visited. It is not an error; it is
content nobody asked for.

Delete the `<SecParent>` line from `tableToCreate` and the run reports
success, writes both files, and the first one contains only its header:

```text
Running sql-tutorial-structured@0.1.0 (m2t) on demo/library-rel
Wrote /home/you/work/generated/Library_rel.sql
Wrote /home/you/work/generated/Library_rel-constraints.sql
```

```text
-- Tables of Library_rel, generated by Synthesis
```

Missing output with an exit code of zero is the characteristic mistake
of this style, and the diagnosis is always the same question: was the
content ever placed?

A misspelled section name fails loudly instead, because a reference has
to resolve:

```text
Error: Transformation 'sql-tutorial-structured' failed: Not existing object
referenced with name "tabels" by element '/DefaultSchema/M2T_Schema/Section'
```

`$refByName` resolves against what is already in the store, so the
section being named has to have been created first. The template
satisfies that by construction: the documents and their empty sections
are written before the rules that fill them.

## What decides the order

Inside a section, the order is the order in which content was placed
into it, which is the order the rules ran. `tablesOf` returns the
tables in the order they appear in the schema, so the `CREATE TABLE`
statements come out in that order, exactly as in Part 1.

What changed is not the ordering rule but what it applies to. In Part 1
one loop wrote into one place, and the order of the file was the order
of the loop. In Part 2 two loops write into two different sections, and
each section is ordered by its own loop. The order of the file is no
longer the order in which the template happens to mention things.

## Sections produce no text of their own

Nothing on this page changes what a section contributes to the output,
which is nothing. `tables-header`, `tables`, and `table_Book` produce
no text of their own; they group paragraphs, and the file is the
concatenation of the paragraphs in tree order.

Their names are not decoration either. They are element names in a
model, which means they are subject to the same uniqueness rule as any
other element name, and `table_${tab.name}` is qualified with the table
name for exactly that reason. Two sections named `table` would be a
duplicate name, not two sections.
