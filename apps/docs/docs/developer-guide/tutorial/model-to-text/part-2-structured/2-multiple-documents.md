# 2. Multiple documents

Part 1 emitted one `<Doc>` and got one file. The rule behind that is
the whole of file layout in Synthesis: **every document in the result
model becomes one file.** So a second file is a second `<Doc>`, and
there is nothing else to learn about it.

What is worth the page is why this generator wants a second file, and
what the rules look like once one walk over the schema feeds one
document and another walk feeds the other.

## Why the constraints move to their own file

Part 1 wrote each foreign key as an inline clause:

```text
CREATE TABLE Book (
  bookId INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  bookTitle VARCHAR(255),
  AuthorId_FK INTEGER REFERENCES Author(authorId)
);
```

That statement can only be applied to a database in which `Author`
already exists. For the Library schema an ordering exists that
satisfies every clause, so the file works. In general no such ordering
exists, because references can be circular: two tables can reference
each other, and a table can reference itself. There is no first table
to create.

Production DDL solves this by separating the two concerns. Every table
is created without its foreign keys, and the foreign keys are added
afterwards, when every table exists:

```text
CREATE TABLE Book (
  bookId INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  bookTitle VARCHAR(255),
  AuthorId_FK INTEGER
);
```

```text
ALTER TABLE Book ADD CONSTRAINT fk_Book_AuthorId_FK
  FOREIGN KEY (AuthorId_FK) REFERENCES Author(authorId);
```

Two kinds of statement, applied in order, with the second depending on
all of the first. That is a property of the artifact, not a preference
about formatting, and the natural way to express it is two files.

## The second document

```tsx
        <Doc name={`${s.name}-constraints.sql`}>
          <Sec name="constraints-header">
            <P>{`-- Foreign key constraints of ${s.name}, generated by Synthesis`}</P>
            <P>{`-- Apply after ${s.name}.sql: references may be circular, so`}</P>
            <P>{'-- every table has to exist before any of them is constrained.'}</P>
            <P>{' '}</P>
          </Sec>
          <Sec name="constraints"></Sec>
        </Doc>
```

The same shape as the first document: a header section with fixed
content, and an empty `constraints` section for the rules to fill. The
header says out loud what the reader of the generated file needs to
know, which is that this file is applied second and why.

## The rule that fills it

```tsx
/** One foreign key: the column that points, and the column it points at. */
type ForeignKey = {
  table: rmT.ITable
  column: rmT.IColumn
  targetTable: rmT.ITable
  targetColumn: rmT.IColumn
}
```

An `ALTER TABLE` statement needs four names, and the model holds them
in three different places: the table a column belongs to, the column
itself, and, through the `references` link, the column it points at
plus the table that owns it. The local type collects them so the rule
that formats the statement does no navigation at all.

```tsx
  // Every referencing column of the schema, paired with the table and
  // column it points at. A column is a foreign key exactly when it has a
  // reference, so this walk is the complete list.
  private foreignKeysOf(s: rmT.IRelSchema): ForeignKey[] {
    const tables = this.tablesOf(s)
    const keys: ForeignKey[] = []
    for (const table of tables) {
      for (const column of table.columns ?? []) {
        if (column.references) {
          keys.push({
            table,
            column,
            targetTable: this.tableOwning(s, column.references),
            targetColumn: column.references
          })
        }
      }
    }
    return keys
  }
```

This is Part 1's `if (c.references)` test, moved out of the line
formatter and into a walk of its own. `tableOwning` is Part 1's helper,
unchanged: a column has no back link to its table, so the table a
reference names is found by searching the schema.

Separating the walk from the formatting is what makes the rest
straightforward:

```tsx
  // The same top-level shape, placed into the second document instead.
  // Nothing but the section name decides which file this ends up in.
  foreignKeyToAlter(fk: ForeignKey): ExprNode<m2tmm.ISection> {
    const constraint = `fk_${fk.table.name}_${fk.column.name}`
    return (
      <Sec name={`constraint_${fk.table.name}_${fk.column.name}`}>
        <SecParent $refByName="constraints"></SecParent>
        <P>{`ALTER TABLE ${fk.table.name} ADD CONSTRAINT ${constraint}`}</P>
        <P>{`  FOREIGN KEY (${fk.column.name}) REFERENCES ${fk.targetTable.name}(${fk.targetColumn.name});`}</P>
        <P>{' '}</P>
      </Sec>
    )
  }
```

Put this rule beside `tableToCreate` from the previous page and they
are the same shape: a named section, a `SecParent` naming where it
goes, and paragraphs. The only difference between a rule that
contributes to the first file and a rule that contributes to the second
is the name in its `SecParent`. Neither rule mentions a document, and
neither knows which file it is writing.

That is the payoff of the previous page. Rules produce content and
declare where it belongs; the template decides what documents exist.
The two can be changed independently, which is what Part 3 goes on to
exploit.

The constraint name is derived rather than invented:
`fk_Book_AuthorId_FK` is the table and the column. Constraint names
have to be unique in a schema and are what a later migration uses to
drop a constraint, so deriving them from the model is what makes
regenerating the file produce the same names again.

## The column rule loses a branch

```tsx
  private columnLine(c: rmT.IColumn): string {
    const parts: string[] = [c.name, c.type]
    if (c.isKey) {
      parts.push('PRIMARY KEY')
    }
    if (c.isAutoincrement) {
      parts.push('AUTOINCREMENT')
    }
    if (!c.isNullable) {
      parts.push('NOT NULL')
    }
    return parts.join(' ')
  }
```

Compared with Part 1, the `if (c.references)` branch is gone, and the
schema parameter with it, because nothing in this method needs to look
anything up any more. The same fact about the model, a column having a
`references` link, is still what produces a foreign key. It is read in
one place instead of two, and it produces a statement in the other file
instead of a clause in this one.

## Two limits worth knowing

**Documents are files in one flat directory.** Every document is
written directly under `--out-dir`. The text metamodel does declare a
`Directory` concept, and the components file exports a `Dir` tag, but
the generator currently reports only the bare document name to the CLI,
so wrapping documents in a directory does not create one: the files
land at the top level anyway. A fix is in progress. Until it lands,
plan for a flat set of files, and put any grouping you need into the
file names, as this package does with `Library_rel-constraints.sql`.

**Two documents cannot share a name.** Documents are model elements,
and element names are unique across a whole model rather than per
container. Give both documents the same name and the run fails while
the model is still being built, before any file is written:

```text
Error: Transformation 'sql-tutorial-structured' failed: newModelElement:
Duplicate name "//www.aelastics.org/Library_rel_sql/Library_rel.sql"
```

The name in the message is the qualified element name, which is the
model's name followed by the element's. In practice the rule costs
nothing, since two documents with the same name would be two files with
the same path, which was never going to work. It is worth recognizing
the message, because it names the metamodel's rule rather than the file
system's, and it is the same rule that makes the section names on the
previous page carry their table name.
