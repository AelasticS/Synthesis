# Part II: decision-based transformations

Part I hard-coded every design choice. Real transformations contain
questions with several defensible answers: should a 1:N relationship
become a foreign key or a join table? Auto-increment keys or manual
ones? snake_case or camelCase? Synthesis makes such questions first
class. The transformation declares variation points, a decision model
declares the design space, a binding model scopes each issue to the
metamodel concepts it concerns, and a configuration model closes the
decisions for one concrete run.

This part walks through the decision-based EER to relational
transformation. The finished package is
[examples/eer-to-relational](../examples/eer-to-relational/); every
listing below is taken from it.

## The cast of models

- **Decision model**: the design space as data. Issues (open questions)
  with options (admissible answers), one of which may be the default.
- **Binding model**: connects issues to the metamodel concepts they
  apply to, optionally narrowed by a condition.
- **Configuration model**: one concrete answer set for one source
  model. Generated by the CLI, editable by you, passed to a run.
- **Trace model**: generated by every run; records which rule (and for
  variation points, which option) produced which target element.

## Step 1: the decision model

`src/decision-model.tsx` declares three issues:

```tsx
export const RelationSchemaDesignIssues = (store: ModelStore): ExprNode<t.IDecisionModel> => (
  <DecisionModel name="RelationSchemaDesign" description="Design space for persistence strategies" store={store}>
    <ElementIssue name="OneToManyStrategy" description="How to implement 1:N relationships">
      <Option name="ForeignKey" description="Use Foreign Key in the Many side table" isDefault={false}
              optionType={<SimpleOption name="FK" />} />
      <Option name="JoinTable" description="Use a separate join table" isDefault={true}
              optionType={<SimpleOption name="JoinTableOption" />} />
    </ElementIssue>
    <ElementIssue name="PrimaryKeyStrategy" description="How to implement primary keys">
      <Option name="UseAutoIncrement" description="Database auto increment" isDefault={true}
              optionType={<SimpleOption name="PK_AutoInc" />} />
      <Option name="UseManualIncrement" description="Use manual increment" isDefault={false}
              optionType={<SimpleOption name="PK_ManInc" />} />
    </ElementIssue>
    <ModelIssue name="NamingConvention" description="How to name the database tables">
      <Option name="CamelCase" description="Use camelCase for table names" isDefault={false}
              optionType={<SimpleOption name="CamelCaseOption" />} />
      <Option name="SnakeCase" description="Use snake_case for table names" isDefault={true}
              optionType={<SimpleOption name="SnakeCaseOption" />} />
    </ModelIssue>
  </DecisionModel>
)
```

Issue kinds differ in scope: an `ElementIssue` is decided per source
element (each relationship can choose its own strategy), a `ModelIssue`
once per model, and a `GlobalIssue` (used by the rel-to-sql-ddl
example) once regardless of the model. Names are load-bearing: issue
names match `@VarPoint` names in the transformation class, and option
names match its `@VarOption` declarations.

## Step 2: the metamodel part

The binding model must point at metamodel concepts, so the package
ships the EER metamodel as a model (`src/er-metamodel.tsx`, a
types-metamodel model named `ERMetamodel` with objects like
`Attribute`, `Entity`, `Relationship`). It is declared as a manifest
part and rendered into the store before the models that reference it.

## Step 3: the binding model

`src/binding-model.tsx` wires issues to concepts:

```tsx
export const ER_Bindings = (store: ModelStore): ExprNode<t.IBindingModel> => (
  <BindingModel name="ER_Bindings"
    sourceModel={<Model $refByName="//www.aelastics.org/ERMetamodel" />}
    decisionModel={<DecisionModel $refByName="//www.aelastics.org/RelationSchemaDesign" />}
    store={store}>
    <Binding name="PKStrategyBinding"
      element={<ModelElement $refByName="//www.aelastics.org/ERMetamodel/Attribute" />}
      issues={[<ElementIssue $refByName="//www.aelastics.org/RelationSchemaDesign/PrimaryKeyStrategy" />]} />
    <Binding name="OneToManyBinding"
      element={<ModelElement $refByName="//www.aelastics.org/ERMetamodel/Relationship" />}
      issues={[<ElementIssue $refByName="//www.aelastics.org/RelationSchemaDesign/OneToManyStrategy" />]}
      condition='return (e) => {
                if (!e.roles || e.roles.length !== 2) return false;
                const m1 = e.roles[0];
                const m2 = e.roles[1];
                return (m1.ub === "1" && m1.lb === "0" && m2.ub === "M") ||
                       (m1.ub === "M" && m2.ub === "1" && m2.lb === "0");
            }'
    />
  </BindingModel>
)
```

References are absolute store paths into the models rendered before
this one (the metamodel part and the decision model). The `condition`
narrows an element issue to the elements it really concerns: here,
OneToManyStrategy is raised only for relationships that are actually
1:N. A design space with only global issues needs no bindings at all;
the rel-to-sql-ddl example's binding model has an empty body.

## Step 4: variation points in the transformation class

The class now extends `DecisionAwareM2M` and receives a configuration
model:

```tsx
@M2M()
export class EER2RelDomainWithDecisionTransformation extends DecisionAwareM2M<
  IEERSchema, rmT.IRelSchema, {}, cm.IConfigurationModel
> {
```

Each open question is a method annotated `@VarPoint`, whose body only
throws; each answer is a `@VarOption` method:

```tsx
  @E2E()
  @VarPoint("OneToManyStrategy")
  RelationshipMapping(rel: IRelationship): ExprNode<rmT.IColumn> | ExprNode<rmT.ITable> {
    throw new Error("Not implemented VarOptions for VarPoint RelationshipMapping")
  }

  @Default()
  @VarOption("RelationshipMapping", Option("ForeignKey"))
  relationshipAsForeignKey(rel: IRelationship): ExprNode<rmT.IColumn> { /* ... */ }

  @VarOption("RelationshipMapping", Option("JoinTable"))
  relationshipAsJoinTable(rel: IRelationship): ExprNode<rmT.ITable> { /* ... */ }
```

At run time the engine dispatches each `@VarPoint` call to the
`@VarOption` whose option the configuration selected for that element
(or model, or globally). `@Default()` marks the fallback used when no
configuration covers the issue. Decorator order matters and the
example documents it in place: `@E2E` (tracing) is outermost so it
wraps the dispatch, and `@VarPoint` must be applied before the
`@VarOption` decorators register against it.

A variation point does not have to produce a new element. The
ForeignKey option returns a reference node that grafts a column into a
table that already exists:

```tsx
    return (
      <Table $refByName={this.applyNaming(pkSide.domain.name)}>
        <Column name={this.applyNaming(fkSide.domain.name + "Id_FK")} ... />
      </Table>
    )
```

## Step 5: the manifest grows a parts block

```json
"parts": {
  "metamodels": [
    { "module": "./dist/er-metamodel.js", "exportName": "EERModel" }
  ],
  "decisionModel": { "module": "./dist/decision-model.js", "exportName": "RelationSchemaDesignIssues" },
  "bindingModel": { "module": "./dist/binding-model.js", "exportName": "ER_Bindings" }
}
```

Parts are modules the package ships and the CLI renders into the store
before every run, in a fixed order: metamodels first, then the decision
model, then the binding model (each may reference what came before).
`decisionModel` and `bindingModel` must be declared together, and their
presence is what makes the transformation decision-based; there is no
separate flag.

## Step 6: running means deciding

Decisions are never applied silently. Run without saying how to decide
and the CLI aborts before any engine work (exit code 2), teaching both
ways out:

```bash
synth transformation run eer-to-relational --in demo/library --out demo/library-rel
```

The two ways:

- `--default-configs` generates a configuration from the declared
  defaults, prints every choice, and proceeds:

  ```
  decision NamingConvention -> SnakeCase (default)
  decision for element bookId: PrimaryKeyStrategy -> UseAutoIncrement (default)
  decision for element writtenBy: OneToManyStrategy -> JoinTable (default)
  Wrote demo/library-rel (...)
  ```

- `config init` writes that same default configuration into the
  workspace as an editable model, for runs with `--config`:

  ```bash
  synth config init eer-to-relational --for demo/library
  ```

`transformation show eer-to-relational` lists the issues and options at
any time; it reads them from the decision model, the single source of
truth.

## Step 7: flip a decision

Open the generated configuration model (`demo/library-cfg`). Each
decision is a `Choice` selecting an option by reference. The 1:N
relationship's choice looks like this:

```tsx
<ElementChoice name="ec_writtenBy"
  element={<Element $refByName="//www.aelastics.org/Library/writtenBy" />}
  choices={[
    <Choice name="ec_writtenBy_JoinTable"
      issue={<ElementIssue $refByName="//www.aelastics.org/RelationSchemaDesign/OneToManyStrategy" />}
      selectedOption={<Option $refByName="//www.aelastics.org/RelationSchemaDesign/JoinTable" />} />,
  ]}
/>
```

Change the selected option (and, for tidiness, the choice name) from
`JoinTable` to `ForeignKey`, then run with the edited configuration:

```bash
synth transformation run eer-to-relational --in demo/library --config demo/library-cfg --out demo/library-rel-fk
```

Compare the two outputs. With the default JoinTable the schema has
three tables:

```tsx
<Table name="book"> ... </Table>
<Table name="author"> ... </Table>
<Table name="written_by">
  <Column name="author_id_fk" type="INTEGER" isForeignKey={true} references="author" ... />
  <Column name="book_id_fk" type="INTEGER" isForeignKey={true} references="book" ... />
</Table>
```

With ForeignKey the join table is gone and the N-side table gains the
key, expressed as a graft into the existing table:

```tsx
<Table name="book"> ... </Table>
<Table name="author"> ... </Table>
<Table $refByName="book">
  <Column name="author_id_fk" type="INTEGER" isForeignKey={true} references="author" isNullable={true} />
</Table>
```

Same source model, same transformation, different architecture. That
is the variability mechanism in one picture.

## What can go wrong

- `--config` and `--default-configs` are mutually exclusive, and both
  are rejected on a transformation that is not decision-based.
- A configuration is checked before use: it must have been generated
  for this transformation, binding model, and source model, every
  choice's issue must exist, and every selected option must belong to
  its issue. Issues the configuration does not cover fall back to their
  defaults, announced as `(default)`.
- Editing option references by hand risks typos; the structural check
  catches them and names the offending choice.

## Where you are

You can now declare a design space, bind it to a metamodel, implement
its options as variation points, and drive runs with configurations.
The [rel-to-sql-ddl](../examples/rel-to-sql-ddl/) example shows the
same machinery on a text generation with a single global issue.
