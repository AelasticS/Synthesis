# simple-eer-to-relational-variability

Configuration-based model-to-model transformation, the simple example with variability:
an EER schema (`simple-eer-metamodel-variability`: schema, entities, attributes,
domains, and relationships with two roles) becomes a relational schema
(`simple-relational-metamodel-variability`: schema, tables, and columns). Three
design issues are closed per run by a configuration model:

| Issue | Level | Options (default marked) |
| --- | --- | --- |
| `OneToManyStrategy` | element | `ForeignKey` (default), `JoinTable` |
| `PrimaryKeyStrategy` | element | `UseAutoIncrement` (default), `UseManualIncrement` |
| `NamingConvention` | model | `CamelCase` (default), `SnakeCase` |

The manifest's `parts` render the EER metamodel-as-model, the decision
model, and the binding model into the store before every run.

## Run

The commands work for both ways of getting the example. Where a path
differs, the tarball form uses `$EX`, the
[examples folder](https://AelasticS.github.io/Synthesis/developer-guide/examples#running-an-example)
of the `synth` installation, and the repository form is relative to this
directory.

- **Tarball install.** The `synth` download ships this example built and
  ready to install. Nothing to build.
- **Repository checkout.** Build the package from the repository root, then
  run the `synth` commands from this directory.

### 1. Install and import

Tarball install:

```bash
EX=/usr/local/synth/examples      # Windows PowerShell: $EX = 'C:\synth\examples'

synth init
synth namespace mk demo
synth transformation install $EX/simple-eer-to-relational-variability
synth model import $EX/simple-eer-to-relational-variability/sample/company.eer.tsx \
  --as demo/company                                                  # Listing 1
```

Repository checkout:

```bash
# build: also builds the two metamodel packages it depends on
rush build -t simple-eer-to-relational-variability

cd examples/simple-eer-to-sql-variability/eer-to-relational
synth init
synth namespace mk demo
synth transformation install .
synth model import sample/company.eer.tsx --as demo/company      # Listing 1
```

### 2. Generate the default configuration (Listing 8)

The default configuration is not written by hand: `config init` runs the
transformation's default-configuration generation on the source model and
saves one default choice per issue, global and per element.

```bash
synth config init simple-eer-to-relational-variability --for demo/company --out demo/company-cfg
synth config show demo/company-cfg                                 # print every decision (Listing 8)
```

To run with the defaults directly, without saving a configuration, use
`--default-configs`:

```bash
synth transformation run simple-eer-to-relational-variability --in demo/company \
  --default-configs --out demo/company-default-rel
```

### 3. Edit the configuration (Listing 9)

The edited configuration is a separate model, `demo/company-edited-cfg`,
so the default one stays available for comparison. Either edit a copy
yourself:

```bash
synth config init simple-eer-to-relational-variability --for demo/company --out demo/company-edited-cfg
synth config edit demo/company-edited-cfg   # opens $EDITOR; change a choice, e.g. OneToManyStrategy
# optional: save a copy as the Listing 9 file
synth model export demo/company-edited-cfg --to company.edited-cm.tsx
```

or, instead, import the saved edited configuration. A configuration model needs
`--tx` to render, and `--dependency` names its source model:

```bash
# tarball install
synth model import $EX/simple-eer-to-relational-variability/config/company.edited-cm.tsx \
  --as demo/company-edited-cfg \
  --tx simple-eer-to-relational-variability --dependency demo/company

# repository checkout
synth model import config/company.edited-cm.tsx --as demo/company-edited-cfg \
  --tx simple-eer-to-relational-variability --dependency demo/company
```

Then compare it with the default one from step 2: the choices changed
from the defaults lose their "(default)" mark.

```bash
synth config show demo/company-edited-cfg
```

### 4. Run with the edited configuration (Listings 10 and 11)

```bash
synth transformation run simple-eer-to-relational-variability --in demo/company \
  --config demo/company-edited-cfg --out demo/company-rel --trace demo/company-trace

synth model export demo/company-rel   --to company.rel.tsx         # Listing 10
synth model export demo/company-trace --to company.trace.tsx       # Listing 11
```

The run prints each decision it applied, e.g.
`decision for element Employment: OneToManyStrategy -> JoinTable`.
The trace records each executed rule as a `RuleInvocation`; its
`Resolution` points at the choices that decided it and says whether the
option was chosen by default.

`npm test` (after the build) runs the CLI smoke plus
[`scripts/verify.mjs`](scripts/verify.mjs), which runs the default and the
edited configuration and asserts the exact tables and the trace
resolutions.

The mapping rules and the design space are explained on the page
[A simple EER to relational transformation, with variability](../../../apps/docs/docs/developer-guide/examples/simple-eer-to-sql-variability.md).
